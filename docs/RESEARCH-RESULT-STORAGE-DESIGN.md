# Result storage redesign

November 25, 2026. The owner explicitly chose to redesign result storage to preserve the full search feature while keeping total monthly spending below US$5. This extends the original serverless PRD's storage implementation scope; it does not authorize a paid plan or an increased budget.

## Design work

- [x] Frame: preserve complete result values, counts, discovery order, all three completed-result sorts, arbitrary supported pagination, query identities, cancellation/fencing, expiry and private recovery.
- [x] Fan out: two independent designs grounded in the existing worker, API, migrations and recovery code.
- [x] Cross-judge: root reviewed both complete designs and evidence. A separate-vendor judge was unavailable; no such review is claimed.
- [x] Pick: compare concrete storage, network, request-count and memory bounds.
- [x] Graft: combine only compatible improvements into one ownership model.
- [x] Verify: both prototypes preserved all 319,352 retained result rows before production persistence changes began.
- [ ] Implement and qualify: migrate all callers, preserve historical results, run local and hosted fault/recovery checks, and reassess the complete monthly envelope.

The design must pass five criteria: exact observable parity; safe atomic publication and stale-worker fencing; bounded PostgreSQL/R2/runtime usage compatible with the monthly limit; independently recoverable private backups and correct retention; and a small, maintainable read/write interface. Estimates do not count as measured acceptance.

Two designs will use the available parent model independently. The skill's default Claude/Gemini runners and a separate-vendor judge are unavailable in this environment; their absence will remain explicit in the synthesis.

## Grounding

The current PostgreSQL model stores one JSONB payload and sort metadata per configuration. The retained publication has 319,352 results, and its complete local database allocates 936,752,819 bytes. Two 2 GiB reservations plus 1 GiB headroom require 6,305,461,939 bytes with that baseline. The 2 GiB reservation is itself an estimate, not a demonstrated bound for every million-result query.

Neon Free source browsing, restricted permissions, private Cloud Run deployment, idle reconciliation, R2 backup and managed restore have passed their scoped rehearsals. New searches remain paused. PostgreSQL should retain durable query identity, permissions, admission, leases, dispatch and publication metadata. The redesign may move bulky immutable result material to private R2 without exposing downloads, bucket credentials or signed object URLs to visitors.

The API exposes partial results in discovery order and completed results sorted by active traits, total cost or champion names, with configuration key as the tie-breaker. Page size ranges from 1 to 200. Retain complete/incomplete distinctions and existing saved-link behavior.

The cost review must include backup retention, operation rounding, transfer out of Google, failed attempts and orphan objects. Avoid a small-object design whose copies exhaust R2's Class A free allowance, and avoid downloading an entire result set for every API request. A hard byte/request allowance must reject work honestly without publishing truncated results as complete.

## Decision and evidence

Select candidate B's frozen `dictionary-result-v1` format. Each record stores its original discovery ordinal and up to eight dictionary member codes in exactly 25 bytes. The dictionary captures complete member values and every trait evaluation variant, so decoding does not call the current solver or a mutable ruleset. Encoding requires exact canonical equality; unsupported payload shapes fail explicitly. No generic fallback is needed for either retained query.

| Criterion | Candidate A: compressed full JSON frames | Candidate B: frozen dictionary records |
| --- | --- | --- |
| Observable parity | All 319,352 rows and four order streams matched; 424 page checks | All 319,352 rows and four order streams matched; 48 page checks |
| Publication and fencing | Immutable packs, fenced SQL pointers, explicit reader/GC lock protocol | Immutable packs, fenced SQL pointers, compact SQL partial tail |
| Storage bound | Observed final layouts 116,866,785 bytes with Zstandard; no small universal compressed bound | Final layouts plus shared dictionary 24,109,878 bytes; exactly 75 MB of final record bytes per million rows |
| Recovery | Self-contained copies and an independent logical digest | Same recovery closure, including frozen dictionary and SQL tail |
| Maintenance | Generic payload support, compression dependency and frame index | Fixed versioned decoder and simple offsets; new payload versions require qualification |

Neither prototype establishes Cloud Run runtime, peak memory, live recovery or the complete monthly invoice. Candidate B's Windows prototype took 85.016 seconds including SQL reads, encoding, four orders and page verification; peak process working set was 110,698,496 bytes. These are local prototype measurements, not a hosted search benchmark. Its full-fixture tuple hash matched the previous experiment: `75f6934b8e08c9a3f3cd89eee0889cf0821c343a8841eb53a785d57ab8852f47`.

Graft candidate A's read/GC protocol: result requests use READ COMMITTED, acquire the shared per-query advisory lock, then read one joined run/generation descriptor. GC takes the exclusive lock and the existing global backup exclusion lock. Readers hold their lock through bounded object reads; no guessed grace period or per-request persistent read lease is needed. Workers append immutable objects and atomically publish their references, without deleting old objects.

## Implementation contract

- PostgreSQL holds query identity, leases, a current generation pointer, at most 4,095 compact tail rows (102,375 bytes), and immutable segment/pack references. A sealed partial segment and each independently hashed completed-sort frame contain 4,096 records. Pages contain at most 200 results and read at most two data segments/frames plus the dictionary. Using this segment size instead of the prototype's 1,000 rows cuts upload round trips by about four, at the cost of a larger bounded SQL tail; database churn still needs measurement.
- A generation uses a unique 32-character hexadecimal namespace. Every upload gets a committed intent with its exact key, size and checksum before network work. A lost acknowledgment stays charged and invisible. The attempt has a 112 MiB cumulative object allowance and at most 248 objects: one dictionary, 244 partial segments and three final packs. These bounds do not replace account-wide admission and monthly operation accounting.
- Final packs contain raw 25-byte records with no header. SQL holds the count, order, object checksum and frame checksums. The dictionary is capped at 4 MiB. Worker scratch is independently capped at 512 MiB; SQLite ordering indexes avoid an untracked external sort. Hosted memory and timing remain qualification gates.
- Claim/retry clears the visible generation pointer and count together. Publication checks the current generation, running state, owner and unexpired lease while holding the query row lock. Completion exposes all three verified packs and terminal counts in one transaction. Incomplete queries retain discovery order.
- New object storage is an explicit deployment mode. The PostgreSQL adapter remains for the existing VM and historical recovery during migration; there is no dual write. Serverless cutover requires all retained results to be migrated and verified first.
- API, worker and recovery credentials use separate bucket permissions. The API gets read-only results access. Source and backup credentials never enter the API service. Credential labels do not determine access; live allowed and denied operations qualify each credential.

Implementation and hosted acceptance remain in progress. Searches and schedules remain paused until the outstanding checks and revised all-provider budget pass.

## Production codec measurements

The [retained-data replay](../projects/research-workspace/verification/serverless-result-codec.json) checked all 319,352 payloads, their original discovery ordinals and logical metadata, both independent champion-set counts, and all eight full ordering streams against PostgreSQL C collation. Every comparison passed with the production 25-byte record format and 16 KiB decoded-result limit. Each generation's dictionary occupied 156,942 bytes. The larger query used 98,390,016 bytes of SQLite scratch and 126,444,316 bytes including four validation packs. The full check took 162.781 seconds in one local Windows run; peak process working set was 173,957,120 bytes, including the harness's retained record lookup.

The [million-result capacity check](../projects/research-workspace/verification/serverless-result-million.json) processed one million distinct eight-member configurations drawn from the 26 longest-name distinct champions in the retained dictionary. Exact record round trips, independent champion-set counts and pack hashes passed. SQLite occupied 405,753,856 bytes; SQLite plus four 25,000,000-byte packs occupied 505,753,856 bytes, below the enforced 536,870,912-byte scratch ceiling. Peak process working set was 104,103,936 bytes. This synthetic check took 302.844 seconds in one local run. It does not establish a universal scratch bound for every future dictionary; exceeding the enforced allowance must stop the attempt explicitly.

The [read-only migration plan](../projects/research-workspace/verification/serverless-result-migration-plan.json) built eight objects totaling 24,265,284 bytes for the two retained queries: one dictionary and three completed-sort packs per query. This production total includes separate dictionaries and differs from the earlier prototype's shared-dictionary layout. Versioned logical checksums include original ordinals and full values. Planning took 151.906 seconds and made no target or cloud changes. This run predates the physical budget-receipt integration and does not qualify transfer, publication or recovery.

The [live R2 transport check](../projects/research-workspace/verification/serverless-result-transport.json) used separate scoped credentials and passed exact byte ranges, immutable write retries, wrong-content rejection, API write denial and operator copies in both directions between the results and archive buckets. It consumed 28 HTTP attempts: eight Class A, seventeen Class B and three deletes. The conservative possible-write total was 458,767 bytes; all three temporary objects were deleted and their absence verified. Copy transport used the production conditional headers with direct boto3 while receipt integration was being developed. It did not exercise database copy receipts or ambiguous-write recovery.

These are correctness and bounded-capacity observations, not a speed comparison. Each duration is from one run, CPU contention and performance limiters were not recorded, and the earlier harnesses did not embed the Python version or contemporaneous production source hashes. Published reports preserve the original report and harness hashes and identify source hashes captured afterward. None establishes Cloud Run runtime, API latency under load, hosted recovery or the complete monthly invoice.

The [local service, data and solver batch](../projects/research-workspace/verification/serverless-result-local-tests.json) passed 325 tests against fresh isolated PostgreSQL 17 databases with migrations 001 through 010. Real retained-bundle checksums and the available solver snapshot were included. One file-symlink protection test was skipped because the Windows account cannot create file symlinks; directory-junction checks ran. The report records source hashes and the sole harness correction: supplying the complete bundle directory instead of its artifact subdirectory. Later migrations and implementation changes need separate follow-up qualification.

The [managed-permission CI rehearsal](../projects/research-workspace/verification/serverless-result-managed-tests.json) passed six install/login/backup/restore tests followed by thirteen existing managed-operations tests, with no skips. A separate fresh PostgreSQL 17 instance required SCRAM passwords and rejected a deliberately incorrect password. The migration owner had neither superuser nor BYPASSRLS, and the recovery test used real PostgreSQL dump/restore clients. CI now supplies dedicated budget databases and runs this managed fixture before the existing operations suite. Workflow YAML and bootstrap syntax were checked locally; the GitHub-hosted workflow and Linux resource limits were not exercised by this Windows rehearsal.

After migration 011 added on-demand capacity collection, a [fresh follow-up](../projects/research-workspace/verification/serverless-result-followup-tests.json) passed all 321 service tests available to this Windows account, retaining the same single file-symlink skip. All nineteen managed-permission and recovery tests also passed against another fresh SCRAM-authenticated cluster with migrations 001 through 011. Source hashes remained unchanged during both runs. These local tests exercise the collector's rejection and admission behavior; they do not qualify live Neon measurement.

## Private provider migration

The [metadata allocation stress test](../projects/research-workspace/verification/serverless-result-metadata-capacity.json) held an old repeatable-read snapshot while two runs each made three million-row attempts. Each attempt wrote 1,000 result checkpoints plus 120 extra maximally sized, incompressible tails. Allocated growth was 403,983,196 bytes for all six attempts. The private configuration therefore reserves 256 MiB per admitted run and 128 MiB additional headroom. This local PostgreSQL allocation test deliberately exaggerates tail churn; it is not a solver benchmark or a provider usage sample.

The [hosted schema installation](../projects/research-workspace/verification/serverless-result-schema.json) applied additive migrations 009 and 010 to the paused Neon source. All five actual runtime logins were denied direct accounting-table updates, and the provider baseline remained unchanged. The explicit resource window includes prior usage, reserves all three search attempts before acceptance and never resets counters automatically. Retained storage survives window changes and uncertain network outcomes. The [revised finite rehearsal](RESEARCH-SERVERLESS-REHEARSAL.md) reserves US$4.91 against the unchanged US$4.99 total ceiling, including all 21 billable secret versions and twelve operator invocations.

The [live historical migration](../projects/research-workspace/verification/serverless-result-migration.json) preserved all 319,352 rows in eight verified R2 objects totaling 24,265,284 bytes. Full logical hashes, original discovery ordinals, independent champion-set counts, query metadata and subscription identities were checked before publishing each generation. The source used a read-only repeatable-read transaction and was not changed. Migration took 243.953 seconds from this Windows client, including encoding, SQL traffic, R2 transfers and decoded verification. It consumed one of twelve operator allowances; it is not a hosted worker timing result.

Before publication, the control plane showed four paused schedules, no pending wakeup tasks and no outstanding Jobs. Runtime database logins were temporarily disabled and their sessions terminated to prevent writes during conversion. The [object-aware release](../projects/research-workspace/verification/serverless-result-runtime.json) is now deployed and that fence is released. Historical API pages match the original payloads and ordering. Search admission was briefly enabled for a bounded preflight, then re-paused after readiness exposed stale pooled connections; neither new query was submitted. Hosted exhaustive search, result-bearing backup/restore, load and final public cutover remain pending.

Migration 011 adds an opt-in [Neon branch collector](../projects/research-workspace/verification/neon-capacity-accounting.md) that uses the provider's PostgreSQL size implementation and live enforcement limit. It includes every database and shared relation fork, keeps active reservations charged, and fails closed on unsupported topology or failed measurements. It runs only for new search admission, without a management API key or background database polling. Its [live owner-role check](../projects/research-workspace/verification/serverless-neon-capacity.json) measured 251,084,800 bytes against 1,073,741,824 bytes in 0.062 seconds. The later restricted API check passed at 258,678,784 bytes after creating an additional empty restore target. Two 256 MiB reservations plus 128 MiB headroom fit. This is current-branch logical storage, not history or invoice accounting. Recheck the full branch and prospective source copy after the new searches before restoring; the earlier projection left only 19,849,216 bytes spare while preserving the old recovery database.
