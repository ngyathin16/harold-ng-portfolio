## Budget decision and next qualification

Unconditional five-minute database polling on Neon Launch costs about US$19.08/month for idle compute alone in a 30-day month. Ten-minute checks still cost US$9.54. Free's 1 GB storage cap is not compatible with the current retained data and admission headroom; reducing retention is not authorized merely to meet this budget. Cloud SQL's displayed Iowa shared-core micro rate alone is US$7.56 per 30 days, before storage; it is not a Singapore quote and does not qualify that option.

Neon **Scale**, despite its name, has no minimum monthly fee and permits one-minute idle suspension. A candidate using 0.25 CU with twelve-minute reconciliation has an idle compute floor of US$3.33 per 30 days, or US$3.441 per 31 days, before startup, useful work, storage, history, Google services and R2. Its US$0.222/CU-hour rate is higher than Launch, but its shorter idle timeout can reduce polling cost. This remains an unqualified candidate: the existing 8 GB planning allocation adds US$2.80 and already breaks the ceiling. Source: [Neon plans](https://neon.com/docs/introduction/plans), [Cloud SQL prices](https://cloud.google.com/sql/pricing).

The [complete local storage experiment](../projects/research-workspace/verification/serverless-storage-options.json) preserved all 319,352 stored result rows and their sort metadata, with identical canonical hashes. Per-row zlib compression reduced the complete one-publication clone from 936,752,819 to 736,564,915 allocated bytes, saving 200,187,904 bytes (21.4%). Only 263,435,085 bytes remained below decimal 1 GB, and migration temporarily needed 1,548,408,499 bytes. Four sort/primary index layouts were preserved. This experiment does not change the production codec, qualify all retained data, or establish provider-billed bytes. The configured result reservations and headroom still exceed Free.

Keeping that measured retained-results baseline, two concurrent 2 GiB reservations and 1 GiB headroom require `936,752,819 + 2 × 2,147,483,648 + 1,073,741,824 = 6,305,461,939 bytes`, approximately **6.305 decimal GB**. A 6 GB allowance therefore does not admit both reservations once those results are retained. Using the source-only import size would omit retained results. This calculation is a local planning requirement; provider-accounted usage, additional publications and operator work still need qualification.

The **2 GiB per-search reservation is an estimate, not a proven storage bound**. The measured JSONB result table and indexes occupy 811,835,392 bytes for 319,352 rows, averaging 2,542.13 bytes per result. Applying that observed average to the configured one-million-result limit gives 2.368 GiB, already above the reservation; an average is not a worst-case bound. The worker's row and time limits do not enforce the reservation as a byte-writing limit. A smaller reservation needs evidence for the exact query/publication domain and PostgreSQL allocation, including indexes and growth; it cannot be justified by making Free appear to fit.

Neon bills storage in **decimal GB (1,000,000,000 bytes)**, using a fixed 744-hour billing month. At Launch's US$0.35/GB-month, 6 GB costs US$2.10 for a full billing month, while 6 GiB costs about US$2.255; 6.5 GB would cost US$2.275 before history and other charges. A proposed three-CU-hour quota costs US$0.318 but permits only 12 total awake hours at fixed 0.25 CU, including maintenance and five-minute idle tails. These are candidate calculations, not a purchased plan or a monthly production quote. [Neon billing units](https://neon.com/docs/introduction/usage-calculations), [plan prices and suspension settings](https://neon.com/docs/introduction/plans).

The replacement keeps five-minute reconciliation and adds a private GCS marker for every accepted generation before database commit. An empty marker listing returns without acquiring a database connection. Transaction locks prevent orphan cleanup racing acceptance; uncertain executions retain markers. Restored or pre-existing work must have markers repaired while dispatch is paused before resume. This removes the compulsory polling floor only when no markers remain; visitors, scheduled operators, readiness checks and capacity collection still cause database usage. The selected capacity collector must refresh on demand or while work is active, rather than recreate permanent idle polling. No timing target or retention requirement was relaxed.

At five-minute cadence, a 31-day idle month makes 8,928 GCS listings. Regional Standard flat-namespace Class A pricing of US$0.005/1,000 gives **US$0.04464** for those listings, before marker creation, tiny object storage, dispatcher compute and other providers. This is arithmetic, not a measured total. The bucket has no automatic expiry: deleting live hints could strand committed work. [GCS consistency](https://docs.cloud.google.com/storage/docs/consistency), [GCS operations pricing](https://cloud.google.com/storage/pricing).

Daily backups also require a recurring network allowance. The existing upload path sends every registered source object through the Google operator into each new R2 backup. The observed 244,066,246 bytes of source objects would alone produce 7,566,053,626 bytes, or 7.046 GiB, over 31 daily backups. At the rehearsal's conservative US$0.23/GiB internet-egress rate, that is about **US$1.621 before database dumps, result inserts, responses or retries**. This is a projection of the measured object inventory, not a measured monthly bill. [Google internet-transfer pricing](https://cloud.google.com/vpc/network-pricing).

The [R2 copy optimization](../projects/research-workspace/ops/backup-README.md) is implemented and [live-qualified with synthetic objects](../projects/research-workspace/verification/serverless-r2-copy.json): 19 HTTP attempts, zero retries, 781 bytes in seven new objects, with no pre-existing objects changed or deleted. Verified source objects are copied within R2 into each backup's own namespace, with signed source and destination conditions and mandatory destination SHA-256 readback. This preserves self-contained backups and retention while avoiding those repeated source-body uploads. **The currently deployed image, whose digest begins `494`, still uses the old upload path**; the optimization's network savings must not be credited to that image or its rehearsal. A subsequent image must include and qualify the change.

Even after that deployment, database dumps and result persistence still send bytes from Google to external providers. Source/destination verification reads, retained R2 storage and request counts also remain. The copy qualification does not establish those monthly volumes, a database restore, or normal production below US$4.99.

## Workload assumptions

The illustrative month is 30 days (720 hours). Use real billable instance time after rehearsal; simultaneous HTTP requests share instance time. Inputs below are planning assumptions, not extrapolated local solver benchmarks. They describe a possible recurring workload, not the current private rehearsal: all four deployed schedules are paused, and paid Neon capacity has not been selected.

| Quantity | No visitors, schedules enabled | Expected illustration | Configured compute envelope |
| --- | ---: | ---: | ---: |
| Browse requests/month | 0 | 100,000 | Read quota 600/minute; unmetered infrastructure probes mean no complete public request-cost ceiling |
| New searches/month | 0 | 300 | At most 4 launch attempts/minute; 2 outstanding executions globally |
| Paid attempts/search | 0 | 1.1 (330 total) | Application at most 3; platform Job retries 0; launch attempts also bounded |
| Search allocation | 2 vCPU, 2 GiB | 2 vCPU, 2 GiB | Same |
| Assumed search billed duration | 0 | 180 seconds including startup, compilation, search, persistence, shutdown | 300-second task timeout; 120-second solver target remains separate |
| API billed instance-seconds | 0 | 20,000 | At most 2 instances continuously busy, subject to platform scaling behavior |
| Dispatcher executions | 8,640 at 5-minute cadence | 8,640 plus 330 wakeups | At most 2 instances; 180-second request timeout |
| Assumed idle/expected dispatcher instance-seconds | 43,200 (5 seconds/run) | 44,850 | Measure empty reconciliation; maximum per-call bound is not the expectation |
| Operator executions | 30 backups + 30 prunes + 30 cleanups | Same, plus explicit import/restore drill | 1 vCPU/4 GiB; 1,800-second task timeout; application deadline 1,500 seconds |

A five-minute reconciler can keep a database with a five-minute idle timeout awake indefinitely. At 0.25 CU continuously awake, Neon compute alone is `720 × 0.25 × 0.106 = $19.08/month`; at 1 CU it is $76.32. Eight GB storage adds $2.80 before history, snapshots and transfer. These are arithmetic illustrations, not a measured Neon quote or an assertion that either compute size passes load.
