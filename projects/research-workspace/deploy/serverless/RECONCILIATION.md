# Finite reconciliation gate

`finite_reconciliation = null` keeps the gate disabled. A reviewed configuration adds one Workflow, one metadata counter in the existing dispatch bucket, two keyless identities and failure alerts. It uses the existing four Scheduler jobs; it creates no extra recurring schedule and invokes no task during Terraform apply.

The fixed reviewed window may span at most 26 hours: up to two hours for private qualification, followed by a full 24-hour no-visitor observation. The five-minute reconciler calls the Workflow during this window. A complete empty marker listing returns before any counter, Cloud Run or PostgreSQL access. Nonempty hints require a successful conditional counter decrement before one POST to the unchanged dispatcher. The source has no retries, loops, connector polling or pagination. Missing/malformed counters, exhausted allowance, failed listings and concurrent compare-and-swap losers fail visibly. Unknown writes consume allowance; they are never retried or refunded. An empty page with a continuation token is not proof of absence.

The metadata counter is specific to `budget_window_id`. Terraform ignores subsequent metadata changes and prevents deletion, so ordinary applies do not refill spent permits. The Workflow identity can GET/UPDATE only this exact object and LIST the bucket; it has no counter create/delete permission. Its code only decrements the remaining value. Changing a window or repairing a counter requires a separately reviewed transition; do not remove protection or reset state to make a plan succeed. Both the object generation and metageneration are checked atomically. [GCS preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)

## Shared execution and cost envelope

Reserve the two delivery paths together. Each accepted query creates one deterministic Cloud Task. Five task attempts use four fast backoffs of 5, 10, 20 and 40 seconds. `max_retry_duration = "0s"` leaves the finite attempt limit in force; a positive ten-minute duration with the same five-attempt setting would allow more attempts because both stop conditions must be reached. The four pause tasks use their own retry override: five attempts, constant 150-second backoff and 600-second duration. [Cloud Tasks retry configuration](https://docs.cloud.google.com/tasks/docs/configuring-queues#set_retry_parameters), [per-task overrides](https://docs.cloud.google.com/tasks/docs/configure-retry-task)

The variable validates `(accepted_queries * 5 + dispatch_limit) * 430 + other_service_cpu_seconds <= 10000`, the corresponding 215 GiB-seconds per call against 5,000, and calls plus other service requests against 500. The 430-second reserve for 1 vCPU / 512 MiB includes 240 seconds of startup, the 150-second application process watchdog, 10 seconds of shutdown and 30 seconds of slack; overlap is counted conservatively. Cloud Run's separate platform request timeout remains 180 seconds. The dispatcher watchdog exits the process if synchronous request work cannot return within 150 seconds, while its main and budget database connections use a 5-second statement timeout and a 3-second lock timeout. Two accepted queries and eight gate calls reserve 7,740 CPU seconds / 3,870 GiB-seconds, leaving 2,260 / 1,130 for previous usage, manual requests and deployment overhead. Declare any already-prepaid requests in `other_service_requests` once; do not add 288 again if the SQL ledger already includes them.

This is finite admission accounting, not a hard provider invoice cap. Cloud Tasks can duplicate or delay delivery, Cloud Run can perform replacement starts, the platform request timeout alone does not terminate an already-running handler, and billing metrics are delayed. Qualify the resource assumptions and all prior/manual usage before enabling the window. [Task delivery limitations](https://docs.cloud.google.com/tasks/docs/common-pitfalls), [request timeout behavior](https://docs.cloud.google.com/run/docs/configuring/request-timeout)

The empty Workflow path has 4 explicit steps, an admitted dispatch 9, exhaustion 6 and a closed window 2. At most 312 nominal five-minute reconciliations fit in 26 hours; 288 belong to the 24-hour idle phase. The empty path would use 1,248 steps across all 312 executions. Keep the existing reserve of 10,000 internal steps, gross US$0.10 after rounding to 1,000-step units without subtracting free credits. The reviewed variable quote becomes US$2.730136 within its existing US$3 allocation and the full reserve stays US$4.91. The extra 24 possible qualification ticks fit the same step, GCS list and alert reserves; empty ticks invoke no Cloud Run service and do not consume dispatch permits. GCS counter operations remain bounded by the same eight permits. The SQL ledger's existing 288 prepaid service requests are retained conservatively; do not add another 24 service requests for empty Workflow ticks. At 31 days of empty five-minute checks, 4 steps each gives 35,712 steps, gross US$0.36 before GCS; this does not approve permanent operation. [Workflows pricing](https://cloud.google.com/workflows/pricing)

## IAM and cloud deadline

The Scheduler loses its direct dispatcher grant when the gate is enabled. Its custom Workflow role contains only `workflows.executions.create`, restricted by the reviewed start/end time. Workflows grants are project-level; there is no supported individual-Workflow IAM/resource-name scope here. Inventory the dedicated project before arming. The gate can invoke only the existing dispatcher during the same window; Tasks invocation expires at the deadline, and the three operator invocation grants use the same start/end window. Audit project/ancestor grants as well: a separate unconditional grant would bypass these conditions. [Workflows IAM](https://docs.cloud.google.com/iam/docs/roles-permissions/workflows), [time-based conditions](https://docs.cloud.google.com/iam/docs/conditions-attribute-reference#date-time)

Error-only call logging has a separate `logging.logEntries.create` grant for the gate identity, expiring one hour after the window. It grants no log read or administration permission. [Workflow logging permission](https://docs.cloud.google.com/workflows/docs/executing-workflow)

The stopper role contains only `cloudscheduler.jobs.pause`. Scheduler also supports only project-level job permissions, so this identity can pause all jobs in this project; the arming inventory must find exactly the four reviewed jobs. It cannot resume, create, edit or run them. Its permission is valid from the deadline until one hour later. Only the independent recovery principal can act as the stopper to create the OAuth-authenticated tasks. [Scheduler IAM](https://docs.cloud.google.com/scheduler/docs/access-control)

`terraform output -json reconciliation_pause_tasks` emits four exact named task requests. They target the existing reconcile/backup/prune/cleanup pause URLs at the expiry time. A pause requires ENABLED state, so a repeated successful pause can produce a later precondition failure. Tasks delivery is best effort; exact PAUSED state at the deadline is not guaranteed. IAM expiry independently rejects new authorized invocations, while already accepted work may finish. Failure and late-attempt alerts reuse the verified channels; late-attempt metrics become available only after an attempt. Current alert pricing begins no sooner than September 1, 2027, so this reviewed rehearsal has no additional fixed alert fee. [Pause API](https://docs.cloud.google.com/scheduler/docs/reference/rest/v1/projects.locations.jobs/pause), [Observability pricing](https://cloud.google.com/products/observability/pricing#pricing-alerting)

## Arming and readback

1. Choose a fresh fixed window no longer than 26 hours, with at least 24 hours left after the intended qualification phase. Refresh all-provider cost/resource evidence and retain room for one backup, one prune and one cleanup inside the 12-operator allowance. Enumerate the actual `03:00`, `05:00` and `06:00` Asia/Hong_Kong cron occurrences in the planned enabled interval; require exactly one of each. For example, 09:00 on day one through 11:00 on day two contains each once. Use the actual dates and future operator-enable time, not this example or a stale saved deadline.
2. Apply the optional gate with both schedule switches false. Verify compiled Workflow source, exact counter metadata, all IAM conditions, queue settings, failure alerts and delivered notification channels. Qualify empty, failed/truncated listing, concurrent counter update, exhausted allowance and unknown POST behavior. Keep provider compilation separate from offline Terraform tests. Existing verified recovery evidence may support the bounded private qualification phase; it does not prove the new result format's recovery.
3. Create exactly the four named output tasks through the independent operator. On uncertain create, GET the same name and compare the entire payload; never blindly submit a new name. Read back schedule time, destination, OAuth account/scope, dispatch deadline and task retry override. Confirm the queue has no routing/authentication override and is RUNNING.
4. Record this task/IAM/readback evidence in `deadline_tasks_evidence`. Reconciliation alone may then be enabled for the bounded full-search/load/recovery qualification, using the existing recovery evidence. Keep operator schedules paused until the new result-format recovery and alerts pass. Configuration validation prevents either schedule switch being enabled with an unrecorded timer setup.
5. Finish qualification within the two-hour buffer. Before starting the no-visitor phase, pause new-search admission, require no outstanding accepted work, pending Tasks or markers, and record the actual phase start with at least 24 hours remaining before the fixed deadline. Enable operator schedules only after the new recovery checks pass and before their three reviewed cron times. If qualification finishes late, record an incomplete 24-hour observation and stop at the existing deadline; do not extend IAM, reset the counter, create a replacement SQL window or move the pause tasks to make it pass.
6. After expiry, read back all four PAUSED states and reconcile executions, counter usage, database wake periods and delayed provider usage. Expired IAM grants remain fail-closed. Review any cleanup or future window separately; never automatically extend an expired allowance. No extra Scheduler job or local process is needed at expiry.
